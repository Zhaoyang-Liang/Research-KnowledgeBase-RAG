可以。下面我按“你已经懂 FHE，但不熟 RLWE / HE 安全参数”的角度讲。核心目标是让你能看懂：

[
(N,\ q,\ QP,\ \chi_s,\ \chi_e,\ H,\ m,\ \lambda)
]

这些东西到底是什么、怎么影响 CKKS/FHE 安全，以及为什么你的 subring/factored bootstrapping 里 leaf 参数不能随便继承 top 参数。

---

# 0. 先给总图

FHE/CKKS 的安全参数大致分两层：

[
\text{功能/正确性参数}
\quad\neq\quad
\text{密码安全参数}.
]

功能参数关心：

[
\text{能不能算完、噪声会不会爆、精度够不够、level 够不够。}
]

安全参数关心：

[
\text{攻击者看到 public key / ciphertext / evaluation keys 后，能不能恢复 secret 或区分密文。}
]

对 RLWE 型 CKKS，安全性主要由以下几项决定：

[
\boxed{
d,\ q_{\max},\ \chi_s,\ \chi_e,\ m
}
]

其中：

* (d)：环维度，也就是 ring degree，例如 (2^{16})。
* (q_{\max})：攻击者能看到的最大模数，不只是当前 ciphertext modulus。
* (\chi_s)：secret key 分布，例如 dense ternary、sparse ternary。
* (\chi_e)：error/noise 分布，例如 Gaussian (\sigma=3.19)。
* (m)：公开 RLWE samples 数量，包括 public key、switching keys、rotation keys、bootstrapping keys。

你的安全草案里其实已经抓住了核心：leaf security 由 ((n,q_{\max},\chi_s,\chi_e,m)) 决定，而不是由 top degree (N) 自动继承。

---

# 1. LWE 是什么，为什么它和安全参数有关

先从 LWE（Learning With Errors）说。

最简化地看，LWE 样本长这样：

[
(a,\ b=\langle a,s\rangle+e \bmod q).
]

这里：

* (a\in\mathbb Z_q^n) 是均匀随机向量；
* (s\in\mathbb Z_q^n) 是 secret；
* (e) 是小噪声；
* (q) 是模数。

攻击者看到很多对：

[
(a_i,b_i).
]

安全假设是：攻击者很难区分这些样本和完全随机的：

[
(a_i,u_i),\qquad u_i\leftarrow \mathbb Z_q.
]

也就是：

[
(a_i,\langle a_i,s\rangle+e_i)
\approx_c
(a_i,u_i).
]

FHE 的 public key、ciphertext、key-switching key 本质上都可以看成某种 LWE/RLWE 样本。所以只要这些样本在参数上足够难，密文就安全。

---

# 2. RLWE 是什么

RLWE（Ring Learning With Errors）是 LWE 的环版本。

普通 LWE 用向量：

[
a,s,e\in \mathbb Z_q^n.
]

RLWE 用多项式环：

[
\mathcal R_q=\mathbb Z_q[X]/(X^d+1).
]

样本长这样：

[
(a,\ b=a\cdot s+e \bmod q),
]

其中：

[
a,s,e\in \mathcal R_q.
]

CKKS/BFV/BGV 都基本基于 RLWE 或其变体。

你可以把 RLWE 理解成：把长度 (d) 的向量组织成一个环元素，这样可以利用 NTT、多项式乘法、SIMD slots 等结构。

---

# 3. CKKS ciphertext 和 RLWE 的关系

CKKS 里一个密文常写成：

[
\ct=(a,b)\in \mathcal R_q^2,
]

满足：

[
b-a s = m+e \pmod q
]

或者有些库用符号：

[
b+a s = m+e.
]

符号正负不重要，本质都是：

[
\text{ciphertext hides }m\text{ under RLWE noise}.
]

攻击者看到 ((a,b))，但不知道 (s)。如果 RLWE 难，那么 ((a,b)) 看起来像随机，因此不泄露 (m)。

---

# 4. 安全参数一：环维度 (d)

环维度 (d) 是：

[
\mathcal R_q=\mathbb Z_q[X]/(X^d+1)
]

里的 (d)。

在 CKKS 里通常 (d) 是 (2^k)。例如：

[
d=2^{16}=65536.
]

一般来说：

[
d \uparrow \quad\Rightarrow\quad \text{安全性上升，但计算变慢。}
]

因为 lattice attack 要处理更高维的格。

你现在的 top/leaf 设置里：

[
N=kn,\qquad n=N/k.
]

top ring degree 是 (N)，leaf ring degree 是 (n)。

安全分析时，leaf ciphertexts 和 leaf keys 要按 (n) 算，不按 (N) 算。

比如：

[
N=2^{17},\quad k=2,\quad n=2^{16}.
]

leaf 安全按 (2^{16}) 算。

如果：

[
N=2^{16},\quad k=4,\quad n=2^{14},
]

那么 leaf 安全按 (2^{14}) 算。即使 top 是 (2^{16})，leaf 暴露对象仍然只有 (2^{14}) 维安全。

---

# 5. 安全参数二：模数 (q)

RLWE 里所有东西都在：

[
\mathcal R_q
]

上。

模数 (q) 越大，攻击者越容易，因为噪声相对于模数更小，样本更接近“无噪声线性方程”。

大致趋势：

[
q \uparrow \quad\Rightarrow\quad \text{安全性下降，但可用计算深度上升。}
]

CKKS 需要很大的 modulus chain：

[
Q=q_0q_1\cdots q_L.
]

bootstrapping 还经常需要 auxiliary modulus：

[
P.
]

所以 key-switching / bootstrapping keys 可能公开在：

[
QP
]

模数下。

安全分析不能只看当前 ciphertext 的剩余 (Q_{\mathrm{ct}})，而要看攻击者能看到的最大公开模数：

[
\boxed{
q_{\max}=\max{Q_{\mathrm{ct}},Q_{\mathrm{eval}},Q_{\mathrm{rs}}P_{\mathrm{rs}},Q_{\mathrm{bts}}P_{\mathrm{bts}}}.
}
]

你现在 Go 实验里 same-(Q) leaf 继承 top 的 (Q/P) basis，日志里主候选 (N=2^{17},k=2,n=2^{16}) 的 `logQP=1520.0`。这意味着 leaf security 要按：

[
d=2^{16},\qquad \log_2 q_{\max}\approx 1520
]

估计。

---

# 6. 为什么 Anyu 那张表很有用

Anyu Wang 那篇 Table 1 给了一个非常有用的参考：在 uniform ternary secret、Gaussian error 标准差 (3.19)、128-bit security 下，不同 (N') 可允许的最大 (\log_2 q)。例如：

[
N'=2^{15}\Rightarrow \log_2 q\approx 868,
]

[
N'=2^{16}\Rightarrow \log_2 q\approx 1747.
]

这张表说明一个重要事实：如果 leaf 是 (2^{15})，但你还给它 same large bootstrapping (QP\approx 1500+) bits，那就不能直接 claim 128-bit。

而如果 leaf 是 (2^{16})，(\log QP\approx 1520)，至少从这类 guideline 表看，它有可能落在合理范围内。但注意：那张表的 secret distribution 是 uniform ternary，不是你当前代码里的 fixed (H=192)。

---

# 7. 安全参数三：secret distribution (\chi_s)

这是你现在最需要理解的部分。

secret key (s) 是一个多项式：

[
s(X)=s_0+s_1X+\cdots+s_{d-1}X^{d-1}.
]

每个系数 (s_i) 怎么采样，就是 (\chi_s)。

常见 secret 分布有：

## 7.1 Uniform ternary secret

每个系数独立从：

[
{-1,0,1}
]

中取值。

通常：

[
\Pr[s_i=-1]=\Pr[s_i=0]=\Pr[s_i=1]=\frac13.
]

所以非零系数比例大约是：

[
\frac23.
]

Hamming weight 期望是：

[
\mathbb E[h]\approx \frac{2d}{3}.
]

例如：

[
d=2^{16}=65536
]

时：

[
\mathbb E[h]\approx 43690.
]

这是 dense-ish ternary secret。

Anyu 的 Table 1 用的是这种类型。

---

## 7.2 Fixed-H sparse ternary secret

你的代码里现在是：

```go
Xs: ring.Ternary{H: 192}
```

也就是固定 Hamming weight 约为 192 的 ternary secret。

这表示：

[
#{i:s_i\neq 0}=192.
]

如果 (d=2^{16})，那只有 192 个非零系数，其余大部分是 0。

这是 very sparse secret。

它性能好，因为 secret 很稀疏，bootstrapping 里的误差范围可能更小。但安全分析更敏感。Sparse secret 不一定不安全，但不能直接套 uniform ternary 的安全表。

Anyu 那篇文章的动机之一就是：sparse secrets 虽然常用于加速 bootstrapping，但 sparse LWE secret 的安全性不够清楚，所以他们用 subring secret encapsulation 把安全基础转向 dense-key RLWE。

---

# 8. 安全参数四：error distribution (\chi_e)

RLWE 样本里有 error：

[
b=a s+e.
]

如果 (e=0)，那攻击者看到的是精确线性方程，很容易恢复 (s)。

所以 error 是安全性的核心。

常见选择是离散高斯：

[
e_i\leftarrow D_\sigma.
]

比如 (\sigma=3.19)。

一般趋势：

[
\sigma \uparrow \quad\Rightarrow\quad \text{安全性上升，但正确性/精度下降。}
]

因为噪声大了，攻击更难；但 FHE 计算也更容易出错。

Anyu 那张 guideline 表用的是 Gaussian error standard deviation (3.19)。

---

# 9. 安全参数五：sample count (m)

攻击者看到的不只一个 RLWE 样本，而是很多：

* public key；
* ciphertext；
* relinearization key；
* rotation keys；
* bootstrapping keys；
* RSDown keys；
* RSUp keys。

每个 key-switching key 里还会有 gadget decomposition digits，对应很多 RLWE encryptions。

所以公开样本数 (m) 也影响安全。

大致趋势：

[
m \uparrow \quad\Rightarrow\quad \text{攻击者信息更多，安全性下降。}
]

有些估计会保守取：

[
m=\infty
]

或者一个很大的上界。如果 (m=\infty) 下都够 128-bit，那基本比较稳。

你的安全草案也强调，最终参数表必须计入所有 public samples，包括 gadget decomposition length 和 evaluation-key components。

---

# 10. HE 安全级别 (\lambda) 是什么

我们常说：

[
128\text{-bit security}
]

意思是最好的已知攻击成本大约是：

[
2^{128}
]

级别。

如果 estimator 输出攻击成本：

[
2^{140}
]

那可以说大约 140-bit security。

如果输出：

[
2^{95}
]

那就是大约 95-bit，不够 128-bit。

最终 scheme 安全级别取最小值：

[
\boxed{
\lambda_{\mathrm{scheme}}
=========================

\min_i \lambda_i.
}
]

对你的 factored route：

[
\lambda_{\mathrm{scheme}}
=========================

\min{
\lambda_{\mathrm{top}},
\lambda_{\mathrm{leaf}},
\lambda_{\mathrm{RSDown}},
\lambda_{\mathrm{RSUp}},
\lambda_{\mathrm{BTSkeys}},
\lambda_{\mathrm{rot}},
\lambda_{\mathrm{rel}}
}.
]

只要某个 leaf object 只有 90-bit，那么整个方案最高只能 claim 90-bit。

---

# 11. 为什么 (q_{\max}) 不能只看 ciphertext modulus

CKKS 里有三类 modulus 容易混：

## 11.1 当前 ciphertext modulus

比如一个普通 ciphertext 当前 level 上可能只有：

[
Q_{\mathrm{ct}}=q_0q_1q_2.
]

这是运行时密文剩余的模数。

## 11.2 bootstrapping modulus

bootstrapping 会 ModUp 到大 modulus：

[
Q_{\mathrm{bts}}.
]

## 11.3 key-switching auxiliary modulus

key switching 往往用：

[
QP.
]

公开 key-switching key 的 RLWE samples 可能在 (QP) 下生成。

所以攻击者看到的最大 modulus 可能是：

[
Q_{\mathrm{bts}}P_{\mathrm{bts}}
]

而不是当前 ciphertext 的 (Q_{\mathrm{ct}})。

安全分析必须用最大公开模数：

[
q_{\max}.
]

这就是为什么你的 same-(Q) leaf 很危险：即使 leaf degree 变小，leaf keys 仍然暴露在 top bootstrapping 级别的大 (QP) 下。

---

# 12. 你的 factored bootstrapping 里哪些对象要估安全

对普通 CKKS baseline，估 top ring 已经很复杂。

对你的 factored route，还要估 leaf ring 和 switching keys。

至少有这些对象：

| Object                          |                Ring degree | 估计重点                                           |
| ------------------------------- | -------------------------: | ---------------------------------------------- |
| top public key / ciphertext     |                        (N) | top RLWE 安全                                    |
| top rotation / relin / BTS keys |                        (N) | top eval key 安全，通常看 (QP)                       |
| RSDown keys                     | 多数按 target leaf ring (n) 看 | source secret under target secret 的 encryption |
| leaf ciphertexts                |                        (n) | leaf RLWE 安全                                   |
| leaf BTS keys                   |                        (n) | leaf bootstrapping key 安全，通常看 (QP)             |
| RSUp keys                       |  多数按 target top ring (N) 看 | leaf-to-top switching key                      |
| output ciphertext               |                        (N) | 输出本身仍是 top ring ciphertext                     |

关键原则：

[
\boxed{
\text{key-switching key 按 target encryption ring / target secret / target modulus 估。}
}
]

因为 key-switching key 通常形如：

[
\operatorname{Enc}_{s'}(g_j(s)).
]

也就是“source secret 的 gadget function 被 target secret 加密”。

# 13. Sparse (H=192) 能不能用

可以用，但要诚实表达。

你的当前 Go 代码用的是：

[
H=192.
]

所以安全表要写：

[
\chi_s=\text{sparse ternary with }H=192.
]

不能写：

[
\chi_s=\text{uniform ternary}.
]

如果你用 lattice-estimator 跑 sparse ternary，就可以得到一个 concrete estimate。这个比自己手推攻击要简单很多。

但论文风险是：sparse-secret estimates 审稿人可能更敏感。你最好写成：

> The prototype uses sparse ternary secrets with (H=192). We report concrete lattice-estimator estimates for this distribution. The security claim is conditional on these estimates and does not rely on dense/uniform-ternary guideline tables.

如果你想走最保守安全路线，则主安全参数最好换成 dense/uniform ternary leaf secret；(H=192) 保留为 performance prototype。

---

# 14. lattice-estimator 在这里扮演什么角色

lattice-estimator 是一个具体安全估计工具。

你给它：

[
(d,\ q_{\max},\ \chi_s,\ \chi_e,\ m)
]

它输出已知攻击模型下的估计攻击成本，例如：

[
2^{120},\quad 2^{135},\quad 2^{160}.
]

它通常会考虑 primal attack、dual attack、hybrid/guessing 等已知格攻击。

它不是数学证明器，而是 concrete security estimator。

你可以理解成：

[
\text{参数} \longrightarrow \text{已知攻击成本估算}.
]

用它比自己推公式简单很多，但你仍然需要懂输入是什么意思，尤其是：

[
q_{\max},\quad \chi_s,\quad m.
]

# 17. FHE 参数选择的三角关系

CKKS 参数永远是在三角形里折中：

[
\text{安全}
\quad
\leftrightarrow
\quad
\text{正确性/精度}
\quad
\leftrightarrow
\quad
\text{效率}.
]

更大 (d)：

[
安全更高，计算更慢。
]

更大 (q)：

[
可计算更深，安全更低。
]

更小 secret Hamming weight：

[
bootstrapping 更快/噪声更小，但安全建模更敏感。
]

更大 error：

[
安全更高，但正确性更难。
]

更多 public keys：

[
功能更强，但安全估计需要计入更多 samples。
]

你的设计在做的是：

[
\text{把大环 bootstrapping 分解到 leaf rings 以换取速度}.
]

但安全代价是：

[
\text{leaf rings 的维度变小，必须重新估安全}.
]
