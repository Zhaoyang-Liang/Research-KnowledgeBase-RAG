不是经验公式，这里应该叫 **implementation scaling correction / implementation normalization factor**，也就是“实现归一化补偿因子”。

这个“补偿逻辑”本质上是 Lattigo bootstrapping 为了让 **ScaleDown、EvalMod、SlotsToCoeffs** 三者的数值尺度匹配，自动或手动调整 `LogMessageRatio`，然后这个调整会传导到 `SlotsToCoeffsParameters.Scaling`。

---

## 1. `LogMessageRatio` 是什么？

它表示：

[
\LogMessageRatio=\log_2\left(\frac{Q_0}{|m|}\right).
]

也就是说，它控制 bootstrapping 前低层模数 (Q_0) 和 message 大小之间的比例。

如果：

[
\LogMessageRatio=8,
]

那么大概意思是：

[
\frac{Q_0}{|m|}\approx 2^8.
]

如果把 `LogMessageRatio` 增加 1：

[
\LogMessageRatio \leftarrow \LogMessageRatio+1,
]

那么：

[
\MessageRatio=2^{\LogMessageRatio}
]

会变成原来的 2 倍。

也就是：

[
\MessageRatio \times 2.
]

---

## 2. 为什么 bootstrapping 需要这个量？

CKKS bootstrapping 里有一个很关键的步骤：**EvalMod**。

大概流程是：

[
\ScaleDown
\rightarrow
\ModUp
\rightarrow
\CtwoS
\rightarrow
\EvalMod
\rightarrow
\StwoC.
]

在进入 EvalMod 之前，密文需要被调整到一个合适的尺度。Lattigo 里 `ScaleDown` 的目标大致是让 ciphertext scale 变成：

[
\frac{Q_0}{\MessageRatio}.
]

也就是说，`MessageRatio` 越大，message 相对于 (Q_0) 越小，EvalMod 的输入范围更安全、更不容易越界。

所以这个补偿的原始目的不是为了你的 no-(B_k) 分解，而是为了：

[
\boxed{
\text{让不同 } \log N/\logSlots \text{ 参数下的 bootstrapping 数值范围和 EvalMod 精度保持稳定。}
}
]

尤其在小 (\log N)、小 (\logSlots) 的测试参数里，Lattigo 示例/测试会提高 `LogMessageRatio`。你 grep 到的代码里就有这种逻辑：

```go
LogMessageRatio += utils.Min(utils.Max(15-LogSlots, 0), 8)
```

以及按 `16 - params.LogN()` 做补偿的写法。

---

## 3. 它为什么会影响 SlotsToCoeffs？

关键在 evaluator 里这两行逻辑：

[
\texttt{offset}
===============

\frac{\texttt{ScalingFactor}}{\texttt{MessageRatio}},
]

[
\texttt{StCScaling}
===================

\frac{\texttt{scale}}{\texttt{offset}}.
]

代入进去：

[
\StCScaling
===========

\frac{\texttt{scale}}
{\texttt{ScalingFactor}/\MessageRatio}
======================================

\frac{\texttt{scale}\cdot\MessageRatio}
{\texttt{ScalingFactor}}.
]

所以：

[
\boxed{
\MessageRatio \times 2
\quad\Longrightarrow\quad
\StCScaling \times 2.
}
]

而 `StCScaling` 最终会乘进：

[
\SlotsToCoeffsParameters.Scaling.
]

所以这条链是：

[
\boxed{
\LogMessageRatio+1
\Rightarrow
\MessageRatio\times2
\Rightarrow
\StCScaling\times2
\Rightarrow
\StwoCScaling\times2.
}
]

这就是你看到 leaf S2C scaling 从：

[
2^{-12}
]

变成：

[
2^{-11}
]

的根本原因。

---

## 4. 为什么 (\log N=16,k=2) 需要除 2？

这组参数是：

[
\log N_{\mathrm{top}}=16,\qquad
\log n_{\mathrm{leaf}}=15.
]

所以：

[
\logSlots_{\mathrm{top}}=15,
\qquad
\logSlots_{\mathrm{leaf}}=14.
]

如果使用：

[
\LogMessageRatio += \max(15-\LogSlots,0),
]

那么 top：

[
15-15=0,
]

不补偿。

leaf：

[
15-14=1,
]

会额外补偿 1。

于是 leaf 的 `MessageRatio` 多乘了 2，leaf 的 `StCScaling` 也多乘了 2。

你的 DFT dump 正好验证了这一点：

[
\StwoCScaling_{\mathrm{top}}
============================

# 0.000244140625

2^{-12},
]

[
\StwoCScaling_{\mathrm{leaf}}
=============================

# 0.00048828125

2^{-11}.
]

C2S scaling 没变，仍然都是：

[
2^{-4}.
]

所以 top 的总线性 scaling 是：

[
2^{-4}\cdot2^{-12}=2^{-16}.
]

leaf 的总线性 scaling 是：

[
2^{-4}\cdot2^{-11}=2^{-15}.
]

两者比例：

[
\frac{2^{-15}}{2^{-16}}=2.
]

所以最终实现里：

[
\BTS_{N,k}^{\mathrm{fac,impl}}
\approx
2\cdot
\BTS_N^{\mathrm{impl}}.
]

因此必须除以 2。你的 (\log N=16,k=2) trace 也显示 leaf linear path 和 final S2C+Merge 的 (\gamma=2)，DIV-2 后误差才降到 (10^{-7}) 量级。

---

## 5. 为什么 (\log N=17,k=2) 不需要除 2？

这组参数是：

[
\log N_{\mathrm{top}}=17,\qquad
\log n_{\mathrm{leaf}}=16.
]

所以：

[
\logSlots_{\mathrm{top}}=16,
\qquad
\logSlots_{\mathrm{leaf}}=15.
]

同样看补偿：

top：

[
15-16<0,
]

不补偿。

leaf：

[
15-15=0,
]

也不补偿。

所以 top 和 leaf 的 S2C scaling 都是：

[
2^{-12}.
]

C2S scaling 也都一样：

[
2^{-4}.
]

于是：

[
\gamma_{\mathrm{impl}}
======================

\frac{2^{-4}\cdot2^{-12}}
{2^{-4}\cdot2^{-12}}
====================

1.

]

所以这组 RAW 直接对齐，不应该除以 2。你的 (\log N=17,k=2) dump 和 trace 都验证了这一点：top/leaf linear path 的 scaling 都是 (2^{-16})，final (\gamma=1)。

---

## 6. 这个补偿逻辑到底“干嘛用”？

一句话：

[
\boxed{
\text{它是为了让不同参数规模下的 bootstrapping 输入范围、EvalMod 近似范围和输出 scale 保持一致。}
}
]

更具体地说，它有三个作用。

第一，控制 ScaleDown 后 message 相对于 (Q_0) 的大小：

[
\text{target scale}\approx \frac{Q_0}{\MessageRatio}.
]

第二，给 EvalMod 留出安全的近似范围，避免 message 太大导致模约化失败或误差变大。

第三，在 EvalMod 之后通过 `StCScaling` 把尺度补回来，让最终输出回到 CKKS 默认 scale。

所以它不是为了 Split/Merge，也不是为了 no-(B_k)。它是 Lattigo bootstrapping 自己的数值尺度管理机制。

只不过你的 no-(B_k) 分解把 top bootstrapping 和 leaf bootstrapping 放在一起比较，于是这个补偿差异暴露成了：

[
\gamma_{\mathrm{impl}}.
]

---

## 7. 最后可以这样理解

理想数学里：

[
\BTS_{N,k}^{\mathrm{fac}}
=========================

\BTS_N.
]

实现里：

[
\BTS_{N,k}^{\mathrm{fac,impl}}
\approx
\gamma_{\mathrm{impl}}\cdot
\BTS_N^{\mathrm{impl}}.
]

其中：

[
\boxed{
\gamma_{\mathrm{impl}}
======================

\frac{
\CtwoSScaling_{\mathrm{leaf}}
\cdot
\StwoCScaling_{\mathrm{leaf}}
}{
\CtwoSScaling_{\mathrm{top}}
\cdot
\StwoCScaling_{\mathrm{top}}
}.
}
]

这个不是经验公式，而是由实现 scaling 推出来的。

对你的两个实验：

[
\log N=17,k=2:
\quad
\gamma_{\mathrm{impl}}=1.
]

[
\log N=16,k=2:
\quad
\gamma_{\mathrm{impl}}=2.
]

原因就是：

[
\boxed{
\logSlots_{\mathrm{leaf}}=14
\text{ 时触发了 } \LogMessageRatio+1
\text{ 的补偿，导致 leaf S2C scaling 多乘了 }2。
}
]

===

有，**有理论支持**，但它不是“密码学安全定理”那种理论，而是 **CKKS bootstrapping 的尺度管理理论 + Lattigo 实现里的 deterministic scaling 逻辑**。

你现在看到的现象，本质是：

[
\boxed{
\text{bootstrapping 过程中，Lattigo 会根据 MessageRatio 调整 EvalMod 和 S2C 的数值尺度。}
}
]

这个调整传到你的 no-(B_k) 分解里，就表现成：

[
\BTS_{N,k}^{\mathrm{fac,impl}}
\approx
\gamma_{\mathrm{impl}}\cdot \BTS_N^{\mathrm{impl}}.
]

## 1. 底层理论：CKKS bootstrapping 不是只做“模约化”，还要管理 scale

CKKS bootstrapping 的核心流程大概是：

[
\ScaleDown
\rightarrow
\ModUp
\rightarrow
\CtwoS
\rightarrow
\EvalMod
\rightarrow
\StwoC.
]

其中 `EvalMod` 要近似计算一个周期函数，把“带有模数 wrap-around 的值”拉回到正确的 message 区间。为了让这个近似多项式有效，输入的 message 大小不能乱来，要控制在一个合适范围内。

所以 Lattigo 引入了一个参数：

[
\MessageRatio = 2^{\LogMessageRatio}.
]

它表示大致的：

[
\MessageRatio \approx \frac{Q_0}{|m|}.
]

也就是说，`MessageRatio` 越大，message 相对底层 modulus (Q_0) 越小，EvalMod 的输入范围越保守。你 grep 到的源码说明 `LogMessageRatio` 默认表示 (Q[0]/|m|) 的 log 比例，`MessageRatio()` 返回 (2^{\LogMessageRatio})。

---

## 2. ScaleDown 为什么用 MessageRatio？

Lattigo 的注释里已经说得很直接：`ScaleDown` 会把 ciphertext level 降到 0，并把 scaling factor 调成类似：

[
\frac{Q_0}{\MessageRatio}.
]

代码注释里写的是：

```go
// ScaleDown brings the ciphertext level to zero and scaling factor to Q[0]/MessageRatio
```

并且它使用：

[
\text{currentMessageRatio}=\frac{Q}{\mathrm{ct.Scale}},
\qquad
\text{targetMessageRatio}=\MessageRatio.
]

这说明 `MessageRatio` 是 bootstrapping 数值尺度管理的一部分，而不是你 no-(B_k) 分解专门引入的东西。

---

## 3. EvalMod 里面为什么也需要 MessageRatio？

EvalMod 近似的是周期函数，例如 mod 1、cos/sin 形式的近似。为了让多项式近似稳定，Lattigo 会把 `LogMessageRatio` 传进 Mod1/EvalMod 参数里。你 grep 到的 `mod1_parameters.go` 里，近似多项式构造时使用了：

[
2^{\LogMessageRatio}
]

作为一个输入参数。

所以理论含义是：

[
\boxed{
\MessageRatio \text{ 决定 EvalMod 看到的 message 尺度和近似区间。}
}
]

当 ring 或 slot 数比较小时，Lattigo 的 test/example 里会增加 `LogMessageRatio`，例如：

```go
LogMessageRatio += utils.Min(utils.Max(15-LogSlots, 0), 8)
```

或者：

```go
LogMessageRatio += 16 - params.LogN()
```

这类补偿的目的就是让小参数下的 bootstrapping 仍然保持合适的数值范围。

---

## 4. 关键：MessageRatio 会传导到 S2C scaling

这就是你看到 (\gamma_{\mathrm{impl}}) 的真正底层原因。

Lattigo evaluator 里有这条逻辑：

[
\texttt{offset}
===============

\frac{\texttt{ScalingFactor}}{\texttt{MessageRatio}},
]

[
\texttt{StCScaling}
===================

\frac{\texttt{scale}}{\texttt{offset}}.
]

代入得到：

[
\StCScaling
===========

\frac{\texttt{scale}}
{\texttt{ScalingFactor}/\MessageRatio}
======================================

\frac{\texttt{scale}\cdot \MessageRatio}
{\texttt{ScalingFactor}}.
]

所以：

[
\boxed{
\MessageRatio \times 2
\quad\Longrightarrow\quad
\StCScaling \times 2.
}
]

而 `StCScaling` 会被乘进：

[
\SlotsToCoeffsParameters.Scaling.
]

你 grep 的结果里也确实显示了：

```go
offset := eval.Mod1Parameters.ScalingFactor().Float64() / eval.Mod1Parameters.MessageRatio()
StCScaling := new(big.Float).SetFloat64(scale / offset)
eval.SlotsToCoeffsParameters.Scaling = StCScaling
```

以及如果已有 scaling，就继续相乘。

这就是底层因果链：

[
\boxed{
\LogMessageRatio
\rightarrow
\MessageRatio
\rightarrow
\StCScaling
\rightarrow
\SlotsToCoeffsParameters.Scaling
\rightarrow
\gamma_{\mathrm{impl}}.
}
]

## 5. 为什么这会影响你的 no-(B_k) 分解？

因为你的 direct 路径和 factored 路径用的是不同 ring degree 的 bootstrapping evaluator：

[
\text{direct: } R_N,
\qquad
\text{leaf: } R_n,\quad n=N/k.
]

每个 evaluator 都有自己的：

[
\CtwoSScaling,\qquad \StwoCScaling.
]

实现上可以抽象成：

[
\CtwoS_N^{\mathrm{impl}}
========================

a_N \CtwoS_N^{\mathrm{ideal}},
]

[
\StwoC_N^{\mathrm{impl}}
========================

b_N \StwoC_N^{\mathrm{ideal}},
]

leaf 上：

[
\CtwoS_n^{\mathrm{impl}}
========================

a_n \CtwoS_n^{\mathrm{ideal}},
]

[
\StwoC_n^{\mathrm{impl}}
========================

b_n \StwoC_n^{\mathrm{ideal}}.
]

如果 Split/Merge、C2S layout、EvalMod 都已经对齐，那么 direct 和 factored 之间剩下的全局比例就是：

[
\boxed{
\gamma_{\mathrm{impl}}
======================

# \frac{a_n b_n}{a_N b_N}

\frac{
\CtwoSScaling_{\mathrm{leaf}}
\cdot
\StwoCScaling_{\mathrm{leaf}}
}{
\CtwoSScaling_{\mathrm{top}}
\cdot
\StwoCScaling_{\mathrm{top}}
}.
}
]

这不是经验拟合，而是线性变换的 scalar factor 直接推出来的。

## 7. 所以“理论支持”是什么？

可以分三层说。

### 第一层：线性代数支持

C2S 和 S2C 是线性变换。如果实现把矩阵乘了一个 scalar：

[
M^{impl}=cM,
]

那么输出必然整体乘 (c)。所以 top 和 leaf 的线性 scaling product 不同，就必然出现全局比例：

[
\gamma_{\mathrm{impl}}=
\frac{c_{\mathrm{leaf}}}{c_{\mathrm{top}}}.
]

这是确定的线性代数，不是经验现象。

---

### 第二层：CKKS bootstrapping 数值尺度支持

EvalMod 要在合适区间近似周期函数，因此 Lattigo 用 `MessageRatio` 控制进入 EvalMod 的数值范围，并在 S2C 阶段通过 `StCScaling` 调整输出尺度。`ScaleDown`、`EvalMod`、`StCScaling` 都围绕这个 ratio 设计。源码注释明确说 `ScaleDown` 的目标是 (Q[0]/\MessageRatio)，而 evaluator 里 `StCScaling` 明确依赖 `MessageRatio`。 

---

### 第三层：你的 trace 实验证明适用前提成立

因为 EvalMod 是非线性的，所以不能只靠线性代数说完。你必须确认 top 和 leaf 进入 EvalMod 的输入是一样的。

你已经做了：

* Split/Merge roundtrip：(\gamma\approx1)；
* C2S blocked alignment：(\gamma\approx1)；
* EvalMod 后 blocked alignment：(\gamma\approx1)；
* 只有 S2C+Merge linear path 改变 (\gamma)。

这说明非线性 EvalMod 没有制造这个比例；比例来自 S2C effective scaling。两个 normtrace 都支持这一点。 

---

## 8. 汇报时可以这样说

你可以直接说：

> 这个 normalization factor 不是经验拟合出来的。它来自 Lattigo bootstrapping 的 scale-management 机制。Lattigo 用 `LogMessageRatio` 控制 (Q_0/|m|)，该 ratio 进入 EvalMod 的数值范围选择，并通过 `StCScaling = scale / (ScalingFactor / MessageRatio)` 传导到 `SlotsToCoeffsParameters.Scaling`。因此，top evaluator 和 leaf evaluator 的 C2S/S2C scaling product 不同，就会产生一个确定的 implementation normalization factor：
>
> [
> \gamma_{\mathrm{impl}}
> ======================
>
> \frac{
> \CtwoSScaling_{\mathrm{leaf}}
> \StwoCScaling_{\mathrm{leaf}}
> }{
> \CtwoSScaling_{\mathrm{top}}
> \StwoCScaling_{\mathrm{top}}
> }.
> ]
>
> 对 (\log N=17,k=2)，这个比值是 1；对 (\log N=16,k=2)，这个比值是 2。

一句话总结：

[
\boxed{
\text{底层就是 CKKS bootstrapping 的 MessageRatio/ScaleDown/EvalMod/S2C 尺度管理机制。}
}
]

你的 no-(B_k) 分解把不同 ring degree 的 evaluator 放在一起比较，所以这个原本隐藏在单个 bootstrapping 里的 scaling convention 被暴露出来了。
