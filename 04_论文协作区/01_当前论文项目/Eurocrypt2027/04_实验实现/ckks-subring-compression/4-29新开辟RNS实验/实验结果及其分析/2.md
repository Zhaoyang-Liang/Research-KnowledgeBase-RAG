## 关键证据

你这次跑的是：

[
Split(ModUp_N(ScaleDown(ct)))
\quad\text{vs}\quad
ModUp_n(Split(ScaleDown(ct))).
]

参数是：

[
\log N=14,\quad k=4,\quad \log n=12,\quad \log(QP)=1400.
]

top 和 leaf 用的是 exact basis，同样的 MaxLevel=22、LogQP=1400，所以这不是因为 Q/P basis 不一致。日志里也显示 leaf params 是 `exactBasis=true`。

最重要的对比是：

[
A = Split(ModUp_N(ScaleDown(ct))),
]

[
B = ModUp_n(Split(ScaleDown(ct))).
]

在 trial 0，leaf 层面 A vs B 的 raw max error 大约是 (5\times 10^5) 到 (6.7\times 10^5)，不是小误差；trial 2 甚至到 (8.97\times 10^5)。拟合一个复数全局 (\gamma) 后误差反而更大，说明这不是简单 normalization/scale factor 问题。

合并回大环后也一样失败：

[
Merge(Split(ModUp)) \approx ModUp_N
]

是对的，误差只有 (2.3\times 10^{-10}) 量级；但

[
Merge(ModUp(Split)) \approx ModUp_N
]

完全不对，误差达到 (1.25\times 10^6) 到 (1.42\times 10^6)。

所以结论是：

[
\boxed{
\text{纯 RNS 层的 split/ModUp 交换成立，但 Lattigo bootstrapping 的 ciphertext-level ModUp 不能这样直接移动。}
}
]

## 为什么会失败

我认为主要原因不是你理论上的 coefficient split 错了，也不是 RNS basis 错了，而是：

[
\boxed{
\text{Lattigo 的 bootstrapping ModUp 不是一个孤立的、纯逐系数 RNS ModUp。}
}
]

它和前面的 `ScaleDown`、参数里的 `LogMessageRatio`、`MessageRatio`、Mod1 scaling convention、以及 top/leaf bootstrapping 参数绑定在一起。

日志里有一个非常明显的信号：

```text
after ModUp_N          Scale exponent = 51
A leaf=Split(ModUp)    Scale exponent = 51
B leaf=ModUp(Split)    Scale exponent = 49
```

也就是说，A 路径继承的是 top ModUp 后的 scale，而 B 路径 leaf ModUp 出来的 scale 少了 2 个 bit。这个已经说明 top ModUp 和 leaf ModUp 的 scaling convention 不一样。

但更重要的是：即使做 fitted gamma，误差也没有变小，反而很大。所以问题不只是差一个 (2^2) 的全局因子，而是 leaf `ModUp` 对输入状态的语义和 top `ModUp` 后再 split 的语义不一致。

## 这说明什么

你前一个纯 RNS 程序证明的是：

[
Split\circ \mathrm{RNSModUp}
============================

(\oplus \mathrm{RNSModUp})\circ Split.
]

这个是正确的。

但这次证明的是另一个事实：

[
Split\circ \mathrm{LattigoBootModUp}_N\circ ScaleDown_N
\neq
(\oplus \mathrm{LattigoBootModUp}_n)\circ Split\circ ScaleDown_N.
]

所以 reduced-(Q) 方向不能简单写成“把 ModUp 移到 Split 后就行”。真实实现里，`ScaleDown+ModUp` 应该被看成一个耦合的 bootstrapping preprocessing block，而不是两个任意可交换的 RNS 操作。

## 下一步应该改测什么

我建议立刻做两个变体，不要继续在当前 B 路径上硬调。

### 变体 1：先 Split 原始低层密文，再 leaf ScaleDown+leaf ModUp

测：

[
Split(ModUp_N(ScaleDown_N(ct)))
]

对比

[
(\oplus ModUp_n\circ ScaleDown_n)(Split(ct)).
]

也就是不要用 top `ScaleDown_N` 后的密文喂给 leaf `ModUp_n`。让 leaf 自己执行完整的 `ScaleDown_n -> ModUp_n`。因为 Lattigo 的 `ScaleDown` 和 `ModUp` 很可能是一对匹配操作。

如果这个过了，说明 preprocessing block 可以整体下放：

[
ScaleDown_N\to ModUp_N\to Split
\quad\approx\quad
Split\to(\oplus ScaleDown_n\to ModUp_n).
]

### 变体 2：leaf ModUp 使用 top 的 Mod1/MessageRatio convention

当前失败里 scale exponent 51 vs 49 很可疑。可以构造一个 leaf evaluator，它的 ring degree 是 leaf，但 `Mod1ParametersLiteral.LogMessageRatio`、ScaleDown target、ModUp scaling convention 尽量和 top 对齐。

要测试的是：

[
Split(ModUp_N(ScaleDown_N(ct)))
]

对比

[
(\oplus ModUp_{n,\mathrm{topConvention}})(Split(ScaleDown_N(ct))).
]

如果这个过了，说明问题主要是 Lattigo top/leaf preprocessing convention 不一致。

## 对 reduced-(Q) 问题的当前判断

现在不能说“降低 Q 可行”。目前只能说：

1. **代数/RNS 层可行**：逐系数 RNS 操作和 coefficient split 交换，这个已经过了。
2. **当前 Lattigo ciphertext-level 调度不可行**：`top ScaleDown -> split -> leaf ModUp` 失败，而且不是简单 normalization。
3. **真正可行的方向可能是整体下放 preprocessing block**：

[
Split
\to
(\oplus ScaleDown_n)
\to
(\oplus ModUp_n)
\to
(\oplus BTSCore_n).
]

也就是说，下一版 reduced-(Q) 研究应该关注：

[
\boxed{
\text{能否把 }ScaleDown+ModUp\text{ 作为整体移到 leaf，而不是只移动 ModUp。}
}
]

这次实验其实很有价值，因为它排除了一个过于乐观的路径。下一步就测 `Split(ctLow) -> leaf ScaleDown -> leaf ModUp`。
