## 1. Sanity check 是通过的

参考路径

[
A=\mathrm{Split}(\mathrm{LattigoModUp}_N(\mathrm{ScaleDown}_N(ct)))
]

本身没有问题。日志里每个 trial 都显示：

[
Merge(A)\approx \mathrm{LattigoModUp}_N(\mathrm{ScaleDown}_N(ct))
]

误差大约是 (2.5\times10^{-10})：

```text
Merge(A) vs Lattigo top ModUp rawMax ≈ 2.5e-10
```

所以 **RingPacking Split/Merge 本身是正常的**，不是它导致失败。

---

## 2. custom ModRaise 没有复现 Lattigo ModUp

你这次定义了：

[
T=\mathrm{Split}(\mathrm{CustomModRaise}_N(\mathrm{ScaleDown}_N(ct))).
]

如果 custom centered ModRaise 和 Lattigo 的 `ModUp` 语义一致，那么应该有：

[
A\approx T.
]

但结果不是。`mulPow2=0` 时：

[
\text{merged }A\text{ vs }T
\approx 1.16\times10^6 \sim 1.56\times10^6.
]

日志 summary 写得很清楚：

```text
worst merged A vs T raw = 1.556949e+06
```

所以当前 custom ModRaise **不是 Lattigo bootstrapping ModUp 的替代品**。

这也解释了为什么之前直接下放 Lattigo `ScaleDown+ModUp` 不行：Lattigo 的 preprocessing 不是一个简单的逐系数 centered lift。

---

## 3. custom ModRaise 的调度兼容性有改善，但远没到通过

最有意思的是：

[
L=\mathrm{CustomModRaise}_n(\mathrm{Split}(\mathrm{ScaleDown}_N(ct))).
]

我们真正想看的是：

[
T\approx L.
]

因为这只比较 custom ModRaise 在 top 后 split 与先 split 后 leaf modraise 的差别。

`mulPow2=0` 时：

```text
worst merged T vs L raw = 3.709732e+05
```

这比

[
A\text{ vs }T,\quad A\text{ vs }L
]

的 (10^6) 量级小了不少，但仍然不是“小误差”。所以结论是：

[
\boxed{
\text{custom RNS lift 比 Lattigo ModUp 更接近可调度交换，但 ciphertext-level RingSwitch/KS 后仍不等价。}
}
]

这个差异大概率来自：一条路径是在高 level 后做 ring switching，另一条路径是在低 level 做 ring switching 后再扩展 RNS。key switching 噪声、gadget 分解、basis extension 的顺序不同，不能期待逐点相等。

---

## 4. `mulPow2` 扫描没有找到隐藏的 (2^p) 缩放

扫描 (p=0,\ldots,12) 的结果也很明确：

```text
pow=0: merged T-L = 3.914e+05
pow=1: merged T-L = 7.532e+05
pow=2: merged T-L = 1.638e+06
...
```

最好的基本就是 (p=0)。继续乘 (2^p) 只会越来越差。

所以这不是简单的：

[
\text{差一个 }2^p\text{ scale factor}.
]

也不是之前那种 normalization factor 问题。

---

## 5. 当前最准确结论

现在三层结论可以这样写：

### 纯 RNS / 明文系数层

[
Split\circ RNSModUp
===================

(\oplus RNSModUp)\circ Split
]

成立。

### Lattigo bootstrapping preprocessing 层

[
Split\circ LattigoModUp_N\circ ScaleDown_N
\neq
(\oplus LattigoModUp_n)\circ Split\circ ScaleDown_N.
]

不成立。

### custom coefficient/RNS ModRaise 层

[
Split\circ CustomModRaise_N
]

和

[
(\oplus CustomModRaise_n)\circ Split
]

比 Lattigo 路径更接近，但 ciphertext-level 下仍有 (10^5) 量级差异，不能当作等价路径直接替换。

---

## 6. 这并不等于 reduced-(Q) 方向失败

这里要换目标函数。

我们现在一直在测：

[
\text{低模数先 split 后 leaf ModRaise 是否等于原始 top ModUp 路径。}
]

但 reduced-(Q) 的真正目标不是逐点复现 top ModUp，而是：

[
\boxed{
\text{低模数 split + leaf 自定义 ModRaise + leaf bootstrapping 是否仍输出正确 plaintext。}
}
]

也就是说，下一步不应该继续强求

[
A\approx L.
]

而应该测：

[
L
\to
\oplus C2S_n
\to
\oplus EvalMod_n
\to
\oplus S2C_n
\to
Merge
]

最终是否接近原始 plaintext。

---

## 7. 下一步实验应改成“功能正确性”而不是“preprocess 等价性”

我建议下一个 probe 测三条完整 bootstrapping 路径：

### Path 0：标准 direct reference

[
ScaleDown_N
\to
LattigoModUp_N
\to
C2S_N
\to
EvalMod_N
\to
S2C_N.
]

### Path 1：top custom ModRaise

[
ScaleDown_N
\to
CustomModRaise_N
\to
C2S_N
\to
EvalMod_N
\to
S2C_N.
]

这个测试回答：

[
\text{custom ModRaise 是否能被 Lattigo 的 C2S/EvalMod/S2C 接受？}
]

### Path 2：leaf custom reduced scheduling

[
ScaleDown_N
\to
Split
\to
CustomModRaise_n
\to
\oplus C2S_n
\to
\oplus EvalMod_n
\to
\oplus S2C_n
\to
Merge.
]

这个测试才回答：

[
\text{低模数先 split，leaf 后 ModRaise，最终 bootstrapping 是否正确？}
]

如果 Path 1 都失败，那说明 custom ModRaise 还没有复现 bootstrapping ModUp 的语义，需要继续 reverse-engineer Lattigo `ModUp`。
如果 Path 1 成功但 Path 2 失败，问题就在 low-level ring switching / KS noise / leaf layout。
如果 Path 2 成功，那 reduced-(Q) 方向就真的有戏。
