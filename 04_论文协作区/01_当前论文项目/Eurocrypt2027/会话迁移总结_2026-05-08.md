## 1. 当前研究主线

我们研究的问题是：

\[
\text{能否把 CKKS Bootstrapping 的核心操作拆到子环上做，从而加速？}
\]

核心路线是：

\[
\mathsf{Split}
\to
\bigoplus_i \mathsf{BTS}_{\mathrm{leaf},i}
\to
\mathsf{Merge}.
\]

其中 \(\mathsf{BTS}_{\mathrm{leaf}}\) 可以是普通 CKKS Bootstrapping，也可以替换成 subKey Bootstrapping。

最重要的理论观察是：

\[
\mathsf{C2S}_N
\to
\mathsf{EvalMod}_N
\to
\mathsf{S2C}_N
\]

这个 CKKS bootstrapping core 可以在理想语义层面分解为：

\[
\mathsf{Split}_k
\to
\bigoplus_{r=0}^{k-1}\mathsf{C2S}_n
\to
\bigoplus_{r=0}^{k-1}\mathsf{EvalMod}_n
\to
\bigoplus_{r=0}^{k-1}\mathsf{S2C}_n
\to
\mathsf{Merge}_k.
\]

这里的关键不是 coefficient split 保持原始大环 slot，而是：

\[
\left(\bigoplus_r \mathsf{C2S}_n\right)\circ \mathsf{Split}_k
=
\Pi_k\circ \mathsf{C2S}_N.
\]

也就是说，split 后 leaf CoeffToSlot 得到的是大环 coefficient-packed slots 的 residue-class grouping。CKKS bootstrapping 的 EvalMod 正好作用在 C2S 后的 coefficient-packed slots 上，因此不需要 \(B_k\) slot-recovery transform。

\[
L^{(1)}=\mathsf{C2S},\qquad

## 3. 关于降低 \(Q\) 的理论结论

最初的问题是：如果把 \(N\) 拆到子环，安全性需要看 leaf 环维度，而不能只看 top ring。

当前使用的粗略 128-bit 参考线：

| 环维度 | 参考上限 |
|---:|---:|
| \(\log N=15\), \(N=32768\) | \(\log(PQ)\approx 868\) |
| \(\log N=16\), \(N=65536\) | \(\log(PQ)\approx 1747\) |
| \(\log N=17\), \(N=131072\) | \(\log(PQ)\approx 3523\) |

重要结论：

1. 对 split route，安全瓶颈通常是 leaf ciphertext / leaf key material，而不是 top ring 的最大可承受 \(Q\)。
2. 如果 top \(=17\)、split 一层，则 leaf \(=16\)，可用 \(\log(PQ)\approx1747\)。
3. 如果 top \(=16\)、split 一层，则 leaf \(=15\)，只可用 \(\log(PQ)\approx868\)。
4. 单纯降低 ciphertext \(Q\) 本身不一定降低当前解密精度，只要 plaintext scale 和 noise 仍然能被低模数容纳。
5. 真正的问题在后续运算，尤其是 leaf bootstrapping 的 CtS/EvalMod/StC 需要 level budget、scale budget 和 noise budget。
6. 低 \(Q\) 会压缩下游 rescale/key-switch/EvalMod 的余量，导致 EvalMod 或线性变换精度下降甚至失败。

对“20 bits 精度”的解释：

若平均误差约为 \(2^{-20}\)，则 Avg L1 precision 约为 20 bits。更一般地：

\[
\mathrm{precision}\approx -\log_2(\mathrm{average\ error}).
\]

所以：

| 精度 | 平均误差量级 |
|---:|---:|
| 20 bits | \(\approx 10^{-6}\) |
| 16 bits | \(\approx 1.5\times 10^{-5}\) |
| 13 bits | \(\approx 1.2\times 10^{-4}\) |
| 9 bits | \(\approx 2\times 10^{-3}\) |

## 4. 应用场景与审稿人质疑的处理

之前讨论过几个应用场景，核心要求是：

\[
\text{需要大 }N\text{ 的 packing/throughput，但 circuit depth 不需要特别大的 }Q.
\]

否则审稿人会问：如果为了安全把 \(Q\) 降低，导致 bootstrapping 更频繁，是否还值得？

一个收益条件可以写成：

\[
B(Q_{\mathrm{leaf}})
\cdot
T_{\mathrm{boot}}^{\mathrm{split}}(N,n,Q_{\mathrm{leaf}})
<
B(Q_{\mathrm{top}})
\cdot
T_{\mathrm{boot}}^{\mathrm{direct}}(N,Q_{\mathrm{top}}),
\]

其中 \(B(Q)\) 表示单位计算需要的 bootstrapping 次数，或者等价地表示在给定 modulus budget 下的 bootstrapping 频率惩罚。

如果降低 \(Q\) 后 bootstrapping 频率上升太多，则 split 加速不一定划算。因此论文中需要明确收益边界：

1. 适合：large packing + moderate depth。
2. 不适合：本来小 \(N\) 就够打包，或者必须依赖极深 \(Q\) chain 的任务。
3. 当前最强实验不是 top16 low-Q，而是 top17 split 到 leaf16 后使用 I1 风格 subKey leaf bootstrapping。

还需要强调：

当前 leaf subKey Bootstrapping 只是第一版融合。理论上还能继续叠加更先进的 leaf bootstrapping 优化，因此收益条件有进一步改善空间。

## 5. subKey Bootstrapping 的理解与命名

统一命名：不要叫 “Anyu Bootstrapping”，应称为 **subKey Bootstrapping**。

参考论文：

```text
01_源文件库/08_文献与引用管理/25- Bootstrapping - AnyuWang.pdf
```

重要理解：

1. subKey 方法不是把原 secret key 真的拆成不安全的小环 key。
2. 它会重新采样一个 subring secret，因此 subKey 本身通常按小环 RLWE 安全性分析。
3. 在论文典型 CKKS 参数中，主要是：

   \[
   N=2^{16},\qquad N'=2^{12}.
   \]

   即向下采样 4 层。

4. dense ternary secret 的 Hamming weight \(h\) 约按 \(N\) 缩小：

   \[
   h'\approx h/16.
   \]

5. EvalMod / digit removal 的范围参数满足：

   \[
   K=O(\sqrt h),
   \]

   所以 \(K\) 约缩小 4 倍。

6. 论文中 subring key switching 的小模数预算约为：

   \[
   \log Q'=45,\qquad \log P'=61,\qquad \log(Q'P')\approx106.
   \]

7. 但是我们当前 split + leaf bootstrapping 的安全瓶颈不只看内部 subKey，还要看刚 split 下来的 leaf ciphertext 及其 bootstrapping 所需 \(QP\)。

这也是为什么：

- top16 -> leaf15 时，\(\log(PQ)\approx927\) 超过 leaf15 的 868 参考线。
- top17 -> leaf16 时，\(\log(PQ)\approx1730<1747\)，安全叙事更干净。

## 10. 构造式低模数小环拆分原型

后来讨论了开放问题：是否能通过构造式方法直接生成低模数 leaf ciphertext，而不是先 full-Q split 再 Resize。

目录：

```text
5-8-lowq-construct/
  main.go
  README.md
```

原型目标：

\[
c_0(X)+s(X)c_1(X)
=
\Delta(P_0(X^2)+XP_1(X^2))+e(X)
\pmod Q.
\]

希望直接构造：

\[
ct_0'\vDash_{R_{n,q}}P_0(Y),
\qquad
ct_1'\vDash_{R_{n,q}}P_1(Y),
\]

其中 \(Y=X^2\)，\(q\mid Q\)。

拆 secret 和 ciphertext：

\[
s(X)=s_0(Y)+Xs_1(Y),
\]

\[
c_0(X)=A(Y)+XC(Y),
\qquad
c_1(X)=B(Y)+XD(Y).
\]

由解密等式推出：

\[
A+s_0B+Ys_1D
=
\Delta P_0(Y)+\nu_0,
\]

\[
C+s_0D+s_1B
=
\Delta P_1(Y)+\nu_1.
\]

于是可以得到 module ciphertext 行：

\[
(A,B,YD),
\qquad
(C,D,B).
\]

再用辅助 key：

\[
\operatorname{KSK}_{(s_0,s_1)\to s'}
\]

把 module ciphertext 切换到普通小环 secret \(s'\)。

toy 实验结论：

1. `ksErr=0` 时，module-to-ring key switching 代数正确。
2. `ksErr=1` 时，最终误差主要来自 toy key switching。
3. 降 \(q\) 本身没有破坏语义；精度主要由 key switching 噪声决定。
4. 当前 toy 不是 Lattigo/RNS/NTT 实现，不能直接当真实性能。
5. 但它说明“构造时直接低 \(q\)”方向是有数学可能性的。


## 15. 不要重复踩的坑

1. 不要把 `layers=1` 理解成只有一个 leaf。它表示 split 一层，得到 2 个 leaves。
2. 不要把 subKey Bootstrapping 称为 Anyu Bootstrapping，论文里统一叫 subKey Bootstrapping。
3. top16 -> leaf15 的 `logQP≈927` 如果完整计入 leaf15 安全预算，是不安全/不干净的。
4. Lattigo SplitNew 后 Resize/drop Q 可以降低输出 ciphertext Q，但不能降低 split key material 的 full-Q 安全问题。
5. 单纯 split/drop/merge 的精度很好，不代表 reduced-Q leaf bootstrapping 一定能工作。
6. L17-I1-CtS55 虽然精度略高，但安全裕量小，不宜作为默认主推。
7. top16 only-split 不应混入成功主表：一个失败，一个归一化错误。
8. `go.mod`/`go.sum` 可能已经被实验改动；下一次动代码前先检查 `git status`。
9. 工作区是 dirty 的，不要随便 revert 用户已有改动。

## 16. 当前最终判断

当前最适合主推的结果是：

\[
\boxed{
\log N_{\mathrm{top}}=17,\quad
\log N_{\mathrm{leaf}}=16,\quad
\mathrm{layers}=1,\quad
\text{leaf subKey Bootstrapping I1}
}
\]

也就是：

\[
\mathsf{Split}_{17\to16}
\to
\bigoplus_{i=0}^{1}
\mathsf{BTS}^{\mathrm{subKey}}_{\log N=16,\log N'=12}
\to
\mathsf{Merge}_{16\to17}.
\]

当前单次实验数值：

```text
logQ ≈ 1425
log(PQ) ≈ 1730
leaf16 安全参考 ≈ 1747
安全裕量 ≈ 17 bits
Avg L1 precision ≈ 19.40 bits
输出计算层 = 15
时间 ≈ 52.03s
相对 only-split ≈ 1.21x
相对 only-subKey ≈ 2.60x
相对 direct ordinary baseline ≈ 2.75x
```

这组结果的论文叙事最干净：安全性基本在参考线内，精度接近 20 bits，输出层数足够，并且相对 only-split、only-subKey、direct baseline 都有可解释加速。
